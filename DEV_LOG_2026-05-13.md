# Dev Log — 2026-05-13

## Goal
Get `ScreenTimeModule` (Expo Module API) properly registered so `requireOptionalNativeModule("ScreenTimeModule")` returns a real object instead of null on device.

## What We Diagnosed

### The symptom
```
LOG  Loaded native modules: []
LOG  ScreenTimeAuthorizationModule: null
LOG  LucidScreenTimeModule: null
LOG  Screen Time auth failed: ScreenTimeModule not available
```

### Root cause chain
1. Old `RCT_EXTERN_MODULE` Swift files in `ios/ScrollTax/` (`ScreenTimeAuthorizationModule.swift`, `LucidScreenTimeModule.swift`, etc.) don't register with React Native 0.81 because the new `ExpoReactNativeFactory` AppDelegate pattern bypasses the old bridge entirely.
2. Rewrote the module as a proper Expo Module API module in `modules/screen-time/ios/ScreenTimeModule.swift`.
3. Expo autolinking must register it via `ExpoModulesProvider.swift`. This file is **generated during `pod install`** (by the `expo-configure-project.sh` Xcode build phase), not statically committed.
4. The `ios/ExpoModulesProvider.swift` that exists in the repo is **empty** — it was generated without the search path to `../modules`.

# Dev Log — 2026-05-14

## What We Did

### Clarified the misleading debug logs
`Loaded native modules: []`, `ScreenTimeAuthorizationModule: null`, and `LucidScreenTimeModule: null` in `app/screens/IOSScreenTimeSetupScreen.tsx` (lines 34–36) are checking the old React Native `NativeModules` bridge. These will **always** be null/empty for an Expo Module API module — they are not indicators of a real problem. The real indicator is `Screen Time auth failed: ScreenTimeModule not available`, which comes from `requireOptionalNativeModule("ScreenTimeModule")` returning null.

### Identified two regeneration points for ExpoModulesProvider.swift
Previously we assumed only the Xcode build phase (`expo-configure-project.sh`) regenerated the file. Discovered there are actually **two**:
1. `use_expo_modules!` during `pod install` — regenerates the file and omits `screen-time` if autolinking doesn't find it on EAS
2. The `[CP-User] [Expo] Configure project` Xcode build phase — regenerates it again at compile time

### Added post_install hook to ios/Podfile
Added two-step fix inside the existing `post_install` block:
1. **Writes the correct `ExpoModulesProvider.swift` content directly** to `ios/ExpoModulesProvider.swift` after `use_expo_modules!` runs — hardcodes `import screen_time` and `ScreenTimeModule.self`
2. **Neutralizes the Xcode build phase** — finds any shell script phase containing `generate-modules-provider` and replaces it with a no-op `echo`, so it cannot overwrite the file at compile time

**Bug found and fixed mid-session:** First version of the hook wrote to `ios/ScrollTax/ExpoModulesProvider.swift` (wrong path). Actual file lives at `ios/ExpoModulesProvider.swift`. Corrected.

### Diagnosed ngrok tunnel issue
`@expo/ngrok` v4.1.3 bundles ngrok binary **v2.3.41**. The auth token being used (`cr_...` prefix) is a **ngrok v3 format token** — incompatible with v2. This caused `TypeError: Cannot read properties of undefined (reading 'body')` on every tunnel start.

Set the token via the npm package (not the global CLI):
```
node -e "require('@expo/ngrok').authtoken('TOKEN')"
```
But `cr_` prefix tokens still fail because they are v3 tokens. Fix: get the correct v2-compatible authtoken from [dashboard.ngrok.com](https://dashboard.ngrok.com), or use `localtunnel` as a no-auth alternative (`npm i -g localtunnel` → `lt --port 8081`).

# Dev Log — 2026-05-20

## What We Found

The dev log entry from 2026-05-14 noted "Bug found and fixed mid-session: First version of the hook wrote to `ios/ScrollTax/ExpoModulesProvider.swift` (wrong path). Actual file lives at `ios/ExpoModulesProvider.swift`. Corrected." — **this correction was never committed**.

The Podfile `post_install` hook was still writing to `ios/ScrollTax/ExpoModulesProvider.swift`. That path is:
1. Not referenced in `ScrollTax.xcodeproj` (grep confirmed zero ExpoModulesProvider entries)
2. Never compiled by Xcode
3. A completely inert write

Meanwhile `use_expo_modules!` generates `ios/ExpoModulesProvider.swift` (root level) and adds it to the xcodeproj. The `already_added` check in the hook found it there and skipped the secondary file add — so the xcodeproj always had the root-level file, but that file had empty/default content (no screen-time) because autolinking couldn't resolve it. The hook's file write went to the wrong path and never helped.

## What We Fixed

Changed `target_provider_path` in the `post_install` hook from:
```ruby
File.join(__dir__, 'ScrollTax', 'ExpoModulesProvider.swift')   # wrong
```
to:
```ruby
File.join(__dir__, 'ExpoModulesProvider.swift')                 # correct
```

Also changed the xcodeproj fallback from `scrolltax_group.new_file(...)` to `project.main_group.new_file(...)` to match the correct file location.

The hook now unconditionally overwrites `ios/ExpoModulesProvider.swift` with hardcoded correct content (`import screen_time`, `ScreenTimeModule.self`) **before** the `already_added` check, guaranteeing the right provider is compiled regardless of what `use_expo_modules!` resolves at autolinking time.

## Signing Architecture

EAS Build flow with local credentials:
1. `eas-build-pre-install` hook → copies extension profiles to `~/Library/MobileDevice/Provisioning Profiles/`
2. `expo prebuild` → plugin runs, reads `certs/*.mobileprovision` to extract UUIDs, sets Xcode build settings
3. `pod install`
4. Fastlane runs `showBuildSettings` → detects all three bundle IDs with their profiles
5. EAS adds all three to `export_options.provisioningProfiles`
6. xcodebuild archives and exports with all targets signed

**Note:** `dist.p12` cannot be opened with the `CERT_PASSWORD=SweetDreams` in `.env`. EAS appears to fall back to its own managed distribution certificate (serial `0F696CAA49DF22FDDFC6F52C0C71134C`). All three provisioning profiles reference this same certificate, so signing is consistent.
